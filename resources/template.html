Which pandoc format actually keeps your document

Every reader and writer pandoc ships was probed with {{NPROBE}} element and feature variants, one at a time. The question each probe answers: can this format tell the rich version apart from the stripped-down one at all - and if it can also be read back, does the AST come home unchanged?

Method

Two questions, two different answers

Expressiveness. For each feature a pair of documents is built: one with the feature (a table cell spanning two columns) and one without it (two plain cells). Both go through the writer. If the bytes come out identical, the format has no way to say it. This needs no reader, so it covers all {{NWRITE}} writers.

Round-trip identity. For the {{NBOTH}} formats pandoc can also read, the rich document is written and read straight back. Exact means the returned AST equals what went in, after normalizing Plain/Para and stripping the document wrappers ipynb, epub and fb2 add. Canonical is the softer verdict beside it: the content came back but the writer restyled it - a default-aligned column reported as left-aligned, a measured column width where the source gave none, raw tex for raw latex, a heading id invented by --auto_identifiers. Counting those as loss overstates pandoc's markdown by eleven probes, so they get their own column instead of being folded either way.

Every writer runs with --wrap=preserve. Without it a wrapping writer turns a SoftBreak into a space, and the probe reads as "cannot express" for a distinction the format handles fine - that alone moved 46 writers.

All figures are the released pandoc 3.10.2. On the 2026-08-17 nightly the djot writer gained raw-content passthrough: its four raw probes (inline and block, html and latex) go from inexpressible to expressed and read back cleanly, taking djot to 56 expressed, 56 round-trip and 35 exact. No other format differs between the two builds.

Expressiveness is the ceiling; exact round-trip is the floor. Between them sits everything that renders correctly but cannot be parsed back - which is most of it.

Headline

Seven things the matrix says

64 / 63

Carve tops the round-trip

Carve is not a pandoc format; it enters through the pandoc-carve bridge, put through the identical probes. Via the exchange AST it expresses 64 features and returns 63 of them unchanged; via .crv source, 63 and 61. Every real pandoc format is behind that on exactness - markdown 46, html 42, djot 33.

63/{{NPROBE}}

HTML is the ceiling for real formats

html, html4/5 and every HTML-backed slide writer (revealjs, s5, slidy, slideous, dzslides) hit 63. The epub writers and chunkedhtml land one behind for different reasons: epub still folds a SoftBreak into a space, chunkedhtml spends a heading level splitting files. The three every one of them misses are latex raw inline and raw block (dropped on purpose) and the 1) vs 1. list delimiter. Nothing else in pandoc's AST is beyond them.

16 / 16

Attributes are the real divider

Ids, classes and key-value pairs are where formats fall apart. HTML and EPUB carry all sixteen attribute probes, JATS 14, djot 13, pandoc markdown 12, latex 10, docx 10, typst 9, ODT only 5 - and fb2, rtf, man, texinfo and haddock zero.

2

Only HTML and JATS do the whole table model

Pandoc's table type has row groups, a row-head-column count, a foot, and attributes on the table, each row and each cell. Only the HTML family and JATS express all eleven table probes. LaTeX, typst, docx, ODT and asciidoc manage nine; djot and markua six; org five.

46/{{NPROBE}}

Pandoc markdown is the best interchange text

It is the only text format that keeps both html and latex raw passthrough (4/4 raw), and it wins the exact round-trip at 46, ahead of html 42 and commonmark_x 39. Everything below that loses more than half.

10/10

Metadata survives in exactly one family

markdown, gfm and commonmark_x round-trip arbitrary YAML metadata - nested maps, booleans, custom keys, all of it. markdown_mmd manages 6.5, LaTeX / JATS / docx / docbook about 4, and djot, rst, mediawiki, ODT, ipynb, rtf and pptx zero.

0

pptx and rtf are one-way doors

The pptx writer expresses 40 features; its reader recovers none of them exactly - it is a text extractor with slide headers. rtf writes 40 and round-trips 26, dropping code, notes, blockquotes and every list style.

Carve

Where Carve lands

Carve has no pandoc reader or writer - it reaches pandoc through pandoc-carve, which maps the Pandoc AST to Carve's own AST and back. That is a different code path from a built-in reader/writer pair, but it answers the same user-facing question, so the identical {{NPROBE}} probes were run through it. Two lanes were measured: through .crv source (what pandoc-carve report.docx -o report.crv produces) and through the Carve exchange AST, which skips the source layer.

{{TCARVE}}

Two things no pandoc format manages: Carve carries the complete attribute model and full raw passthrough in both directions. HTML has the attributes and drops foreign raw; markdown keeps the raw and loses four attribute probes. Outside the AST serializations, nothing else holds both. Carve also returns all sixteen inline probes exactly, which only latex, markdown and native also manage.

Against the formats it is usually compared with, Carve is ahead on both counts: markdown 59 expressed / 46 exact, commonmark_x 57 / 39, djot 52 / 33, gfm 50 / 24. On expressiveness the source lane now ties the HTML family at 63, and the AST lane passes it at 64 - which makes Carve the most expressive non-AST format in the matrix.

What Carve does not carry, and why

  • Column widths are dropped deliberately. Pandoc derives a ColWidth for every grid and multiline table from the ASCII column widths, so the value is usually not the author's and a diagnostic would fire on the ordinary case. Documented policy, not an omission.
  • Example-list numbering ((@)) has no Carve form. The list is emitted as a decimal list, so the resolved numbers survive but the document-wide counter that makes separate lists renumber each other does not. Neither lane returns it - it joins column widths and header-less column alignment as the three probes both lanes miss.
  • A foot and multiple row groups have no pipe-table spelling. They survive whole through pandocToCarveAst; only the pipe source flattens them into body rows, and it reports the flattening. Row-head columns used to flatten the same way and now do not - they reach the source as a ::: list-table with header-cols.
  • Column alignment without a header row has no column-level spelling. docs/extensions.md already lists an aligns= attribute as the follow-up; the per-cell fallback carries it in the meantime, and reports the move.
  • Citations come back as citations, without their definitions. Quoted text, citations and block cells used to change AST shape on the way back and now return unchanged. What a citation still cannot carry is the bibliography: entries live in pandoc metadata, so no [@key]: definitions are emitted and an undefined key renders verbatim.

Reading the result

Picking a target

Need everything preserved. json, native and xml are the AST itself and score {{NPROBE}}/{{NPROBE}} by construction. For anything that has to render, html5 and epub3 are the practical maximum.

Need it back later. carve through pandoc-carve leads at 61 exact (63 via its AST), then markdown 46 and commonmark_x 39. Metadata no longer separates them: markdown and Carve both return all ten meta values.

Print and typesetting. latex 54 and beamer 55 lead, typst 53 is close and loses mostly attributes, context 50 has the better table story but no raw passthrough at all.

Word processing. docx 53 is ahead of odt 47, and much further ahead on attributes (10 vs 5). icml keeps layout but almost no attributes.

Structured publishing. jats 54 is the strongest XML target and the only non-HTML writer with the complete table model; docbook and tei trail at 42 and 40.

Importing. The best sources are html, docx, latex, jats, org, rst, mediawiki and markdown. Avoid pptx and rtf as inputs when structure matters. Twelve input formats - bits, creole, csv, endnotexml, mdoc, pod, ris, tikiwiki, tsv, twiki, vimwiki, xlsx - have no matching writer and are not measured here.

Not document writers at all. csljson, bibtex and biblatex serialize the references metadata and emit nothing for body content; opml keeps only the heading outline. Their low scores describe their purpose, not a defect.

Limits

What these numbers do not say

  • Expressed is not faithful. gfm and markdown_strict "express" colspans and tables by falling back to a raw HTML block. That counts as a difference in the output bytes, and it is genuinely lossless, but the result is no longer that format's own markup.
  • SoftBreak is a flag artifact. Under the default --wrap=auto almost every text writer folds SoftBreak into a space. With --wrap=preserve html, markdown, latex, djot and typst all distinguish it. Treat that one row as noise.
  • Dropping foreign raw is correct. An html writer discarding RawBlock "latex" is target routing working as designed, not a coverage gap. Only formats that host both (markdown, commonmark_x, muse) reach 4/4.
  • Defaults only. No extension tuning, no --columns, no custom templates. Turning on markdown_strict+raw_html or similar moves these numbers.
  • One feature at a time. Interactions are untested - a format may keep an id on a heading and lose it on a heading inside a table cell.
  • Carve is measured through a bridge. The carve and carve-ast rows come from pandoc-carve's own converters, not from a pandoc reader/writer pair. Same probes, same two questions - but a library written against the Pandoc AST has an easier job than a writer constrained by an existing file format's syntax. Read the comparison as "what a user gets", not as a like-for-like implementation contest.
  • pdf is excluded because the writer shells out to an external TeX engine that is not present here. Its fidelity is LaTeX's, minus everything the engine rasterizes away.
  • Binary formats (docx, odt, pptx, epub, chunkedhtml) are compared after unzipping and dropping the timestamp-bearing members, with SOURCE_DATE_EPOCH=0. A determinism control confirmed every format except ipynb produces byte-identical output for identical input.

Reproduce

How it was run

git clone https://github.com/markup-carve/pandoc-format-fidelity
cd pandoc-format-fidelity
make                    # fetch pinned pandoc, run every lane, build the report
make carve CARVE_BRIDGE=../pandoc-carve/dist/index.js   # optional Carve lanes

The probe set lives in src/probes.py: each entry is a pair of pandoc AST block lists differing in exactly one feature. Writer conversions go through pandoc's own HTTP server for speed; the server has no filesystem access, so any media a probe references is handed over in the request; the CLI lanes get the same file through --resource-path. Both had to be fixed - an image pandoc cannot resolve makes epub leave the src alone and round-trip to a false exact.
