Which pandoc format actually keeps your document

Every reader and writer pandoc ships was probed with {{NPROBE}} element and feature variants, one at a time. The question each probe answers: can this format tell the rich version apart from the stripped-down one at all - and if it can also be read back, does the AST come home unchanged?

Method

Two questions, two different answers

Expressiveness. For each feature a pair of documents is built: one with the feature (a table cell spanning two columns) and one without it (two plain cells). Both go through the writer. If the bytes come out identical, the format has no way to say it. This needs no reader, so it covers all {{NWRITE}} writers.

Round-trip identity. For the {{NBOTH}} formats pandoc can also read, the rich document is written and read straight back. Exact means the returned AST equals what went in, after normalizing Plain/Para and stripping the document wrappers ipynb, epub and fb2 add. Canonical is the softer verdict beside it: the content came back but the writer restyled it - a default-aligned column reported as left-aligned, a measured column width where the source gave none, raw tex for raw latex, a heading id invented by --auto_identifiers. Counting those as loss overstates pandoc's markdown by eleven probes, so they get their own column instead of being folded either way.

Every writer runs with --wrap=preserve. Without it a wrapping writer turns a SoftBreak into a space, and the probe reads as "cannot express" for a distinction the format handles fine - that alone moved 45 writers.

These measurements use released pandoc {{PANDOCV}} and were refreshed on {{RUNDATE}}. The current comparison with the preceding measurement is in results/delta.json; dated comparisons are in results/history.jsonl. Carve source, exchange AST, and export-format round trips have separate results below, with the bridge and renderer revisions recorded alongside them.

Expressiveness is the ceiling; exact round-trip is the floor. Between them sits everything that renders correctly but cannot be parsed back - which is most of it.

Carve

Where Carve lands

Carve has no pandoc reader or writer - it reaches pandoc through pandoc-carve, which maps the Pandoc AST to Carve's own AST and back. That is a different code path from a built-in reader/writer pair, but it answers the same user-facing question, so the identical {{NPROBE}} probes were run through it. Two lanes were measured: through .crv source (what pandoc-carve report.docx -o report.crv produces) and through the Carve exchange AST, which skips the source layer.

What Carve does not carry, and why

  • Column widths now cross exactly. Carve's positional widths metadata maps to Pandoc ColWidth, in both source and AST lanes.
  • Example-list numbering ((@)) has no Carve form. The list is emitted as a decimal list, so the resolved numbers survive but the document-wide counter that makes separate lists renumber each other does not. Neither lane returns its document-wide counter.
  • Multiple row groups remain source-only loss. They survive whole through pandocToCarveAst, while source merges body boundaries and reports that flattening. A table foot now crosses through ListTable's footer-rows.
  • Column alignment now has a column-level spelling. Positional aligns metadata preserves it even without a header row.
  • Citations come back as citations, without their definitions. Quoted text, citations and block cells used to change AST shape on the way back and now return unchanged. What a citation still cannot carry is the bibliography - the bridge's own warning says entries live in pandoc metadata, so it emits no [@key]: definitions and an undefined key renders verbatim. The probe carries no bibliography, so that part is the bridge's account, not a measurement here.

Reading the result

Picking a target

Need everything preserved. json, native and xml are the AST itself and score {{NPROBE}}/{{NPROBE}} by construction. For anything that has to render, html5 and epub3 are the practical maximum.

Need it back later. carve through pandoc-carve returns {{CARVE_SOURCE_EXACT}} probes exactly ({{CARVE_AST_EXACT}} via its AST); markdown returns {{MARKDOWN_EXACT}} and commonmark_x {{COMMONMARK_X_EXACT}}. For metadata, scores out of ten are: markdown {{MARKDOWN_META}} and Carve source {{CARVE_SOURCE_META}}.

Print and typesetting. latex 54 and beamer 55 lead, typst 53 is close and loses mostly attributes, context 50 has the better table story but no raw passthrough at all.

Word processing. docx expresses {{DOCX_EXPRESSED}} probes and odt {{ODT_EXPRESSED}}. They express {{DOCX_ATTRS}} and {{ODT_ATTRS}} attribute probes respectively. icml keeps layout but almost no attributes.

Structured publishing. jats 54 is the strongest XML target and the only non-HTML writer with the complete table model; docbook and tei trail at 42 and 40.

Importing. The best sources are html, docx, latex, jats, org, rst, mediawiki and markdown. Avoid pptx and rtf as inputs when structure matters. Twelve input formats - bits, creole, csv, endnotexml, mdoc, pod, ris, tikiwiki, tsv, twiki, vimwiki, xlsx - have no matching writer and are not measured here.

Not document writers at all. csljson, bibtex and biblatex serialize the references metadata and emit nothing for body content; opml keeps only the heading outline. Their low scores describe their purpose, not a defect.

Limits

What these numbers do not say

  • Expressed is not faithful. gfm and markdown_strict "express" colspans and tables by falling back to a raw HTML block. That counts as a difference in the output bytes, and it is genuinely lossless, but the result is no longer that format's own markup.
  • SoftBreak is a flag artifact. Under the default --wrap=auto almost every text writer folds SoftBreak into a space. With --wrap=preserve html, markdown, latex, djot and typst all distinguish it. Treat that one row as noise.
  • Dropping foreign raw is correct. An html writer discarding RawBlock "latex" is target routing working as designed, not a coverage gap. Only formats that host both (markdown, commonmark_x, markdown_mmd, muse) reach 4/4.
  • Defaults only. No extension tuning, no --columns, no custom templates. Turning on markdown_strict+raw_html or similar moves these numbers.
  • One feature at a time. Interactions are untested - a format may keep an id on a heading and lose it on a heading inside a table cell.
  • Carve is measured through a bridge. The carve and carve-ast rows come from pandoc-carve's own converters, not from a pandoc reader/writer pair. Same probes, same two questions - but a library written against the Pandoc AST has an easier job than a writer constrained by an existing file format's syntax. Read the comparison as "what a user gets", not as a like-for-like implementation contest.
  • pdf scores zero because its engine is missing, not because the format is poor. The writer shells out to an external TeX binary that is not installed here, so every pdf conversion errors and the row reads 0. Its real fidelity is LaTeX's, minus whatever the engine rasterizes away.
  • Binary formats (docx, odt, pptx, epub, chunkedhtml) are compared after unzipping and dropping the members that carry a timestamp - core.xml, app.xml, meta.xml. On the path the writer lane actually uses - pandoc's server with standalone off - all 75 checkable writers re-emit byte-identical output for identical input, pdf excepted because it errors; make controls reruns that check. Standalone output is not reproducible in the same way: a CLI epub embeds a random urn:uuid in content.opf and toc.ncx, and ipynb a random cell id.

Reproduce

How it was run

git clone https://github.com/markup-carve/pandoc-format-fidelity
cd pandoc-format-fidelity
make                    # fetch pinned pandoc, run every lane, build the report
make carve CARVE_BRIDGE=../pandoc-carve/dist/index.js   # optional Carve lanes

The probe set lives in src/probes.py: each entry is a pair of pandoc AST block lists differing in exactly one feature. Writer conversions go through pandoc's own HTTP server for speed; the server has no filesystem access, so any media a probe references is handed over in the request; the CLI lanes get the same file through --resource-path. Both had to be fixed - an image pandoc cannot resolve makes epub leave the src alone and round-trip to a false exact.
